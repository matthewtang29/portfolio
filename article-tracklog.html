Building Tracklog

Article · October 2026

Tracklog turns your Apple Music library into a SQL database and shows your listening habits. It runs entirely in your browser.

Try it live ↗ Source on GitHub ↗

Why I made it

I wanted a project that showed real SQL skills on data I actually care about. Apple Music doesn't give you much: no all-time stats, nothing like Spotify Wrapped on demand. What it does give you is a full library export (Library.xml) with every song's play count, skip count, date added and last played.

So the question became: what if that file became a proper relational database, and every stat on the page was just a SQL query you could read?

What it does

You drop in your Library.xml (or try the built-in sample library) and get a dashboard:

  • Total hours listened and a one-line takeaway
  • Top songs and top artists, ranked by hours, with album covers
  • Playlists, each with its most-played song
  • Genres, forgotten favourites (songs you played 30+ times but not in the last six months), and most skipped
  • Added to library by month, with the peak month highlighted
  • A SQL console where you can write your own queries against your own library, with example queries to start from

The file never leaves your computer. There is no server and no account.

The stack

  • Database: SQLite, running in the browser through sql.js
  • Front end: plain HTML, CSS and JavaScript (ES modules). No framework, no build step
  • Album art: Apple's public iTunes Search API
  • Hosting: GitHub Pages

I kept it deliberately small. The whole app is around 1,500 lines, and the SQL lives in its own .sql files so anyone reading the repo can see exactly how each number is calculated.

How it works

Library.xml ─► parse ─► SQLite in the browser ─► one SQL query per card ─► charts
  • Parsing. Apple's export is a plist (a nested XML dictionary format). database.js walks it and pulls out songs, artists, albums and playlists, skipping podcasts, videos, folders and Apple's built-in playlists.
  • Schema. The data goes into a normalized schema: artists → albums → tracks, plus a many-to-many playlist_tracks table. A v_tracks view joins the names back in and computes hours_listened = play_count × duration.
  • Queries. Every dashboard card runs one query from sql/queries/. They use joins, CTEs, aggregation, window functions (ROW_NUMBER, RANK, SUM() OVER), date functions and a named :export_date parameter so "six months ago" means six months before your export, not today.
  • Rendering. render.js turns query results into ranked lists, bars and tables.

Here's one I like. Each playlist's most-played song, in one pass:

WITH ranked AS (
  SELECT p.name AS playlist,
         v.title || ' – ' || v.artist AS top_song,
         ROW_NUMBER() OVER (PARTITION BY p.playlist_id ORDER BY v.play_count DESC) AS rn,
         SUM(v.play_count) OVER (PARTITION BY p.playlist_id) AS plays
  FROM playlists p
  JOIN playlist_tracks pt ON pt.playlist_id = p.playlist_id
  JOIN v_tracks v ON v.track_id = pt.track_id
)
SELECT playlist, plays, top_song FROM ranked WHERE rn = 1 ORDER BY plays DESC;

The hardest part: album covers

Library.xml has no images at all, and a music dashboard without covers looks dead. So I look each song up with the iTunes Search API, which turned out to be the trickiest part of the whole project:

  • Wrong matches. Searching "See You Again" returns a dozen different songs. I match on exact title and artist, prefer the same album, and penalize live, remix, karaoke and cover versions.
  • Missing songs. Some tracks just don't come back from search. Since every song on an album shares a cover, I fall back to any result by the same artist from the same album. That fixed songs like "Pyramids".
  • Never guess. If nothing matches, the tile keeps a plain placeholder instead of showing the wrong cover.
  • Rate limits. iTunes allows roughly 20 searches a minute. Lookups are spaced out, back off for 30 seconds when Apple blocks them, and show "Finding covers… X of Y" while they work.
  • Caching. Every album cover seen in any search result is saved in the browser, so other songs from that album need no request, and repeat visits load instantly.

Artist pictures reuse the same work: each artist's image is the cover of their most-played song, picked in SQL with ROW_NUMBER().

How I built it: vibe coding with AI

I built Tracklog by pairing with Claude, an AI coding assistant. I'd describe what I wanted in plain English, it would write the code, and I'd test it against my own library and push back when something was off.

That loop shaped the project more than any plan did:

  • It started as a Python script. The first version loaded my library into SQLite with Python and printed query results. Moving it into the browser meant anyone could try it without installing anything.
  • The name changed three times. Apple Music analyzer → Liner Notes → Heavy Rotation → Tracklog.
  • The design changed three times. An Apple Music-style pink and red theme, then a dusty rose one, then the current "Ink & Sage" look I mocked up myself: near-black panels, a sage green accent and a fixed sidebar.
  • Real data caught real bugs. Running it on my own 697-song library surfaced things a sample never would, like the wrong-cover problem and Apple's rate limits.

My job was product and judgment: deciding what the dashboard should say, catching when numbers looked wrong, and asking "where's the SQL?" until the code was readable enough to explain in an interview.

Getting it ready to launch

Before sharing it, I ran a full launch, security and privacy pass:

  • Discoverability: proper page title and description, Open Graph tags and a link-preview image, a full favicon set, a sitemap, and a custom 404 page.
  • UX: the upload button above the fold, a sticky upload button on phones, and clear errors for wrong file types or files over 500 MB.
  • Security: a Content-Security-Policy that only allows the few hosts the app actually uses, a strict referrer policy, and a Subresource Integrity hash on the sql.js script so a tampered CDN file won't run.
  • Privacy: a privacy page that matches what the code really does (your library stays in your browser; only the title, artist and album of songs on screen go to Apple for cover lookups, and you can turn that off) and a terms page.

I also turned that pass into a reusable checklist I can drop into future projects.

What I'd add next

  • Listening history over time. Diff weekly library exports to reconstruct play history and find listening streaks (a classic gaps-and-islands SQL problem).
  • Time-of-day patterns once Apple's full privacy export (with per-play timestamps) arrives.
  • Export the built database or any query result as CSV.

What I learned

  • Designing a normalized schema from messy real-world data
  • Writing SQL that's readable, not just correct: CTEs, window functions, parameters
  • Working around a third-party API's limits with matching rules, caching and backoff
  • Shipping a static site properly: SEO, accessibility, CSP and privacy
  • Using AI as a collaborator while staying the one who decides what "right" looks like
